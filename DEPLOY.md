# Deployment

Everything runs on **Render** as Docker containers: the API, the public website
and the admin site. Vercel remains an option for the website (section 2).

## Why the backend is not on Vercel

Vercel's Python functions cap at 250 MB unzipped. The training pipeline's
dependencies measure ~269 MB before any application code:

| Package | Size |
|---|---|
| scipy | 97 MB |
| pandas | 69 MB |
| scikit-learn | 46 MB |
| numpy | 31 MB |
| others | 26 MB |

Three further blockers are independent of size: SQLite and the trained model
artifacts need a filesystem that survives a request, `refresh_fixtures_loop` is
a long-running background task that a serverless function will not run, and
cold-starting a joblib model on every invocation would be slow.

Render runs a normal long-lived container, so all three stop being problems.

## 1. Render (API + websites)

`render.yaml` at the **repository root** is a Blueprint. In the Render dashboard:
**Blueprints → New Blueprint Instance**, point it at this repo and branch. It
creates, all on the free plan:

| Service | Built from | What it is |
|---|---|---|
| `predictor-api` | `artifacts/predictor-api/Dockerfile` | FastAPI backend |
| `predictor-web` | `deploy/web/Dockerfile`, `APP=predictor-web` | Public website |
| `predictor-admin` | `deploy/web/Dockerfile`, `APP=admin-web` | Admin site |
| `predictor-db` | — | PostgreSQL |

The websites are nginx containers serving the built React app. Each forwards
`/api/*` to the API (stripping the `/api` prefix), so the browser only ever
talks to its own domain and CORS never comes into it.

### Secrets to fill in

The Blueprint asks for these (`sync: false`, never read from the repo):

| Service | Variable | Value |
|---|---|---|
| both websites | `API_UPSTREAM` | The API's public URL, e.g. `https://predictor-api.onrender.com` |
| API | `DEFAULT_ADMIN_EMAIL` / `DEFAULT_ADMIN_PASSWORD` | The first admin account (password 12+ characters) |
| API | `PUBLIC_SITE_URL` | The website's URL — OPay returns customers here |
| API | `PUBLIC_API_URL` | The API's URL — OPay posts payment callbacks here |
| API | `OPAY_MERCHANT_ID` / `OPAY_PUBLIC_KEY` / `OPAY_SECRET_KEY` | From the OPay dashboard |
| API | `FOOTBALL_API_KEY` | Optional; without it the keyless ESPN source is used |
| API | `CORS_ORIGINS`, `OPAY_PRODUCTION` | Leave empty |

`JWT_SECRET` and `DATABASE_URL` are generated by Render. With no admin email and
password set, **no admin account is created at all** — there is no default.

The service URLs are only known after creation. If a name is taken Render adds a
suffix, so copy the real API URL from its dashboard page into `API_UPSTREAM`
and `PUBLIC_API_URL`, then redeploy the websites.

### What the free plan means

- **Sleeping.** A service with no traffic for 15 minutes stops; the next visitor
  waits about a minute. The website then waits on the API, which may also be
  waking. Change `plan` to `starter` to keep them running.
- **No persistent files.** Every restart starts from a clean filesystem. The
  schema is migrated automatically at startup, and trained models are copied
  into the database and restored from there, so neither needs a disk.
- **No shell.** Scripts cannot be run on the service itself; run them from your
  own machine against the database instead (below).
- **The free database expires after 30 days.** Upgrade it before then, or move
  to Supabase (section 1b) — otherwise the data is deleted.

### After the first deploy: backfill and train

The API serves fixtures and daily picks immediately, from the Dixon-Coles
engine. The learned tips, the per-fixture analysis and the results tracker need
completed matches, so backfill and train. Use the database's **External
Database URL** (Render → `predictor-db` → Connect):

```bash
cd artifacts/predictor-api
export PREDICTOR_DATABASE_URL="<External Database URL>"
python scripts/backfill_history.py --days 240
python scripts/train_model.py
```

Training on your machine is also faster than the free instance's 0.1 CPU would
be. `train_model.py` stores the models in the database; the API picks them up on
its next prediction request. Until then `/football/tips` returns 503 saying no
model is trained, and the site shows that rather than inventing predictions.

Skip the backfill and every fixture reads "not enough history to analyse" until
enough matches have been played *after* launch — weeks, not days.

## 1b. Using Supabase for Postgres

Supabase can host the database instead of Render's. Nothing in the application
changes: it is SQLAlchemy against Postgres either way, and the config already
rewrites the `postgres://` scheme Supabase hands out into the driver form
SQLAlchemy 2 requires.

Take the connection string from **Settings → Database → Connection string**,
not the REST API URL. The REST URL (`https://<ref>.supabase.co/rest/v1/`) is
PostgREST and is not something SQLAlchemy can connect to.

Supabase offers two:

| Connection | Port | Use for |
|---|---|---|
| Direct | 5432 | Migrations, and long-running servers |
| Transaction pooler | 6543 | Serverless and short-lived connections |

Render runs a normal long-lived container, so use the **direct** connection.
The transaction pooler does not support prepared statements, which SQLAlchemy
uses by default.

```bash
export PREDICTOR_DATABASE_URL="postgresql://postgres:<password>@db.<ref>.supabase.co:5432/postgres"
python scripts/check_database.py     # confirms the link, prints no credential
python scripts/migrate_schema.py     # creates the tables
```

On Render, set `DATABASE_URL` to the same value and drop the `predictor-db`
block from `render.yaml`. Supabase's direct connection is IPv6-only unless you
buy the IPv4 add-on, and Render does not reach IPv6 addresses; use the
**session pooler** (port 5432 on `pooler.supabase.com`) instead, which behaves
like a direct connection.

Two things to know. Free-tier Supabase projects pause after a week of
inactivity and need waking from the dashboard. And the `service_role` key
bypasses Row Level Security completely — it belongs only in server
environment variables, never in the frontend or a repository.

### Row Level Security

This API connects as the database owner and enforces access in application
code, through the existing admin RBAC. RLS is therefore not what protects your
data here — the connection string is. If you later read tables directly from
the browser with the publishable key, RLS becomes load-bearing and every table
needs a policy before that happens.

## 2. Alternative: website on Vercel

`vercel.json` at the repo root builds only `predictor-web` out of the pnpm
workspace.

**Before deploying, edit `vercel.json`** and replace the placeholder host:

```json
{ "source": "/api/:path*", "destination": "https://YOUR-RENDER-HOST/:path*" }
```

That rewrite mirrors what the Express `api-server` does in the Replit setup:
`/api/football/*` on the frontend becomes `/football/*` on the Python API.
Because the rewrite is server-side, browser requests stay same-origin and CORS
never enters into it.

The second rewrite sends every non-`/api` path to `index.html`, which
client-side routing needs — without it, loading `/results` directly returns 404.

Then:

```bash
npx vercel --prod
```

Or connect the repo at vercel.com and let it build on push. Framework preset:
**Other** (the build command is already in `vercel.json`).

## Before you deploy anything

These are unresolved and deploying does not fix them:

- **`JWT_SECRET_KEY` from the original `.env` leak is still valid.** It was
  committed to a public repo. Anyone holding it can forge tokens for any user.
- **The accounts in the committed `football_ai.db` are compromised.**
  `admin@footballai.com`, the `@example.com` demo users, and
  `riotech2222@gmail.com` all had password hashes published. Delete them from
  any live database, and change that password anywhere else it is used.
- **`.env` and `football_ai.db` are still in git history.** Untracking them does
  not remove them. Purging needs `git filter-repo` and a force push.
